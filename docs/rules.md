# 联锁规则系统设计

把原来写死在代码里的联锁判定条件（`sig.depart_checked`、`interlock.clear.releasable`
等）变成可配置、可校验、带版本、可回退的规则。本文档记录架构与关键取舍。

## 总览

```
现场规则簿(JSON) ──► 五级校验 ──► 版本化存储(哈希链) ──► 门控引擎 ──► 判定
                        │              │                  │
                        └──────── 规则审计链(哈希链) ◄──────┘
```

- 规则是**数据**，事实目录是**代码**：现场能调条件与阈值，能引用哪些现场量由
  系统目录（`rules/catalog.py`）决定，目录里的取值限值来自平台配置。
- 一切生效动作产生不可变版本；一切判定与变更写哈希链审计；历史只追加不改写。

## 规则 DSL

JSON 表达式树，无 `eval`、无可执行代码：

```json
{"op": "and", "args": [
  {"fact": "gap.clear"},
  {"op": "ge", "args": [{"fact": "train.dwell_s"}, {"const": 30}]},
  {"op": "in", "args": [{"fact": "signal.aspect"}, {"const": ["green", "yellow"]}]}
]}
```

规则簿按作用域组织（`depart` / `door.open` / `interlock.release` …），每个作用域
是「deny 规则拦异常 + 显式 allow 规则放行正常 + 缺省拒绝」。**放行必须是显式
规则**：删掉 allow 规则的效果是全拒（安全方向），而不是全放。

判定口径（`rules/engine.py`）：

1. 任一 deny 规则命中 → 拒绝；
2. 有规则因缺事实/求值失败无法判定且缺省为 deny → 拒绝（fail-safe）；
3. 有 allow 规则命中 → 放行；
4. 否则按作用域 `default_effect`（安全作用域强制 deny）。

## 校验流水线（不通过不许生效）

五级，逐级短路（`rules/validate.py`）：

| 级 | 拦什么 |
|---|---|
| syntax | 顶层形状、schema 版本、规则必填字段、id 唯一、缺省放行必须是 advisory |
| schema | 表达式树结构：运算符已知、参数个数、`in` 右值是字面量列表 |
| semantic | 事实在目录中、运算符两侧类型相容 |
| range | 数值阈值在事实的物理限值内、枚举取值合法 |
| safety | 恒真/恒假死规则、空规则却缺省放行 |

`activate`/`rollback` 强制重跑校验，不信任调用方"已验过"（配置可能已收紧）。
校验失败写审计链（`validate_failed`），现场能看到每一条为什么被拦。

## 版本与回退

- 每次生效产生不可变 `RuleVersion`：`version_hash` 覆盖版本头与内容哈希，
  `prev_hash` 链到上一版本，篡改可检测。
- **回退 = 生成内容等于目标版本的新版本**（`source=rollback`，记 `rollback_of`），
  不把指针拨回去。历史完整：v1→v2→v3(=v1) 三步都可查。
- 回退前用**当前**目录与校验器重验旧内容：目录随配置演进后，引用已退役事实
  或越界阈值的旧版本拒绝回退（修复前进，不许带病回退）。

### 取舍一：已执行动作不重算

回退**不**重算、不改写已按新版执行的判定。理由：物理动作（门已开、车已走）
无法撤销，回放改判只会制造两套互相矛盾的事实。系统提供
`impact(version)`（该版本期间全部判定记录）供值班员人工处置，审计链里每条
判定都带版本号与事实快照，定责依据完整。

## 生效时机（门控）

### 取舍二：会话钉住，而不是"立即切换"或"等作业结束"

一次列车作业（到站→发车）开工时钉住当时的规则版本，作业全程按这一版判定；
新开工的作业立即用新版本。

- 立即切换：同一趟车的开门、关门、发车可能各按不同口径判定，联锁状态不自洽；
- 等全部作业结束：长停站列车会无限期卡住规则下发；
- 钉住：在途作业口径自洽，新版对后续作业立即生效。两版并存期间
  `GET /api/rules` 能看到每个在途会话钉住的版本，判定记录带版本号，可解释。

会话钉住关系落盘（`rules/sessions`），**重启后在途作业仍按开工时的版本判定**。

## 崩溃安全：单提交点

版本落盘三步（`rules/store.py`）：

1. 写版本文档（临时文件 + fsync + rename）；
2. 追加提交流水（fsync）——**唯一提交点**；
3. 重写 head 指针（原子写）。

崩在第 2 步前：孤儿版本文档，永不生效；崩在第 3 步前：启动时按流水最后一条
commit 重建 head。提交流水是唯一事实来源，head 只是缓存。启动时从创世到 head
逐版本核对哈希链，断链/篡改拒绝启动。规则审计链同理：逐条重算，断链拒起。

部分失败语义：提交点前失败 → 激活整体无效，可安全重试；提交点后失败 →
调用方看到错误但版本实际已生效，**重试前先查 history**（提交流水是事实来源）。

## 并发模型

- 单进程内：服务层 `RLock` 串行化全部写动作（部署形态是单写入进程的控制台
  服务，与现有 `JsonStore` 一致）。
- 调用方层面：乐观 CAS。`activate`/`rollback` 必须带 `base_version`（调用方
  看到的当前版本），与库顶不符即 `RuleConflictError`（HTTP 409）。两个值班员
  同时改，后到者重新拉取再提交，不会互相覆盖。

## 审计：三条记录互相印证

1. **提交流水**：生效的权威记录（版本号 + 链上哈希 + 时间）；
2. **规则审计链**：提案、生效、回退、每次门控判定（含事实快照），哈希链防篡改；
3. **平台审计**：`rule_gate` / `rules_activate` / `rules_rollback` 条目，
   控制台时间线可见。

## 回放

- `replay(decision_id)`：按判定记录里的版本与事实快照重算，结论必须与记录
  一致（判定器是确定性的），不一致即数据被改或求值逻辑已变；
- `evaluate_at(scope, facts, at)`：按时间戳找当时生效的版本判定。
- 回放绝不使用当前版本——规则换过几轮，用新版算旧账没有意义。

## 版本兼容

- 规则簿带 `schema` 字段，本系统支持 `1`；更高的拒绝生效（不能猜着执行）。
- 版本文档不可变，旧版本永远可用旧内容回放；求值语义只向后兼容地扩展。
- 配置（事实限值）收紧后，旧版本内容可能不再通过校验：不影响它作为历史
  回放，但**回退到它会被拒**（见上）。

## 接口

CLI：`python -m psdline rules show|history|catalog|audit|validate FILE|activate FILE|rollback N|impact N|replay ID`

HTTP：`GET /api/rules[/history|/catalog|/audit|/impact]`、
`POST /api/rules/validate|/simulate|/activate|/rollback|/replay`，
只读页面 `/rules`。

## 现场改规则的标准动作

1. 改出规则簿 JSON → `rules validate` 看五级校验结果；
2. `rules activate FILE --author 张 --reason 为什么改`（基线版本缺省取当前，
   并发冲突会 409，重新拉取再提交）；
3. `rules show` 确认版本与在途会话；新作业自动用新版；
4. 出问题 `rules rollback N --reason 为什么退`，再 `rules impact M` 查
   问题版本期间的判定记录，人工处置受影响列车。
